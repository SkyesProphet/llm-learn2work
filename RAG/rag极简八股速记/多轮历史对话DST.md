## 历史轮次的信息如何利用？ DST处理多轮对话？

### 关键术语速记
#### 1. DST（Dialogue State Tracking）
作用：任务型对话系统中，**从用户每一轮对话里，抽取出当前 “需求状态” **。

状态字典是三元组，（domain, slot, value）

1. **Domain（领域）**：是任务型对话系统中的一个**任务**。 
2. **Slot（槽位）**：是domian下需要填的**信息字段**。对话的过程就是不断**填槽、改槽、确认槽**的过程。
3. **Slot Value（槽值）**：是slot对应的具体值。
    举例：（"domain": "restaurant", "slot": "food", "value": "chinese"）
    （"domain": "机票订票"，"slot": "出发地"，"value": "上海"）
4. **Dialogue State（对话状态）**：DST 最终输出的结果。当前所有 slot + slot value 的集合。系统靠此状态决定下一步该问什么、调用什么 API。

#### 2. 状态更新策略
1. 全量预测派：每次都重新预测所有 slot。
   - 每次模型直接遍历所有槽位，对每个 slot 用分类 / 生成模型重新预测一遍值。
   - 优点：逻辑简单，不容易漏槽。 适合slot不多的场景。
   - 缺点：计算量大，slot 一多就很慢。容易受无关信息噪声干扰。

2. 增量更新派：只更新本轮提到的 slot，其他不动。
   - 先有一个提及检测器：判断用户这轮提到了哪些 slot。
   - 只对这些被提及的 slot 做更新。没提到的 slot 保持 keep。
   - 优点：计算量小，适合 slot 多的场景。抗噪声：不会乱改无关槽位。
   - 缺点：逻辑复杂，容易漏槽（若检测器错了）。

#### 3. 多轮历史DST架构
DST 其实是对话系统的记忆模块，它和 NLU、对话管理、NLG 这几个模块是配合工作的。
**典型流水线结构**：
    用户输入 → NLU → DST → DM（对话管理） → NLG → 系统回复
- DST：对话状态追踪，对话系统的记忆模块，维护多轮结构化对话状态。
- NLU：自然语言理解，处理单轮意图与槽位抽取。
- DM：对话管理，依据 DST 状态做决策：追问 / 确认 / 调用 API。
- NLG：自然语言生成，将决策转为自然回复。
核心区别：NLU 看单句，DST 看历史；DM 靠 DST 做动作。

#### 适用场景
不适用：
1. 单轮问答（FAQ），每轮对话独立，无需维护状态。
2. 简单填槽式对话，用 规则匹配 配合 简单的槽位， DST是 过度设计。
3. 开放式闲聊加任务型混合场景。 DST虽然能够 帮助切换上下文，但复杂DST模型推理慢，资源占用高，需要判断是否投入场景。

新方向： Zero-Shot DST
